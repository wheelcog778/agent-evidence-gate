# 案例：一道门怎么从"假"变成"真"

这是 `starter/` 里证据门的真实演化过程。看懂了这一篇，比看十篇架构文章有用。

---

## 起点：只验"文件存在"

```python
if not evidence_path: fail
if not Path(evidence_path).exists(): fail
```

看起来没问题。实际上等于没验——文件可以是空的、可以是抄的、可以是上一轮的。

**它怎么被发现的**：让一个无工具的模型复核 agent 交的 `report.md`，它第一句话就是：

> sha256 只给出结果值，没有产生它的命令行与终端回显，按硬规则「声称通过必须附命令与输出」不可采信。

判 FAIL。它说得对。

---

## 第一轮：加"复现"节

产物里必须有一节 `## 复现`，列出跑过的命令。

**模型复核结果**：仍然 FAIL。

> 命令 [0] 是 `python demo/agent_research.py` 相对路径，在 `work/` 下执行会找不到文件（摘录「## 复现」首句 + 命令 [0]）。

真实问题：相对路径在隔离工作目录里指错地方。

---

## 第二轮：贴全 stdout

之前只贴了 6 行输出，但声称有 11 个标题。

**模型复核结果**：FAIL。

> 命令 [3] 声称列出全部标题，实测 stdout 只到 L47，共 6 行；而结论与证据清单均称标题数 11、列出 11 条。同一份报告内 6 ≠ 11。

真实问题：**截断后自相矛盾**。贴输出就得贴全，或者明确写"共 N 行，以下前 K 行"。

---

## 第三轮：去掉时间戳

日志第一行是 `started=2026-11-08T18:39:03`。

**模型复核结果**：三项 PASS，但指出实质缺陷。

> 命令 [0] 贴出的 stdout 含 `started=...`，重跑必然变化，其 `stdout_sha256` 不可能复算。这与报告「复现」节自述「每条命令的 stdout 应逐字节等于下面贴出的内容」直接冲突。

真实问题：**带时间戳的命令不是纯函数**，它的 hash 永远复算不出来。

改法：时间戳写进另一个文件，不进被 hash 的 stdout。

---

## 第四轮：全 PASS

三项全过，而且模型自己做了交叉验算：

> 证据标题清单 11 行中，以 `## ` 开头者为 10 行，恰等于 `[6]` 的 10，且 11−1=10 与 `[2]` 的 11 自洽。

---

## 然后是外部审查：7 条 P0

我自己觉得已经完成了。让 Codex 做只读对抗审查，15,530 字节，结论是：

> **不能。** 至少修完 P0 中的执行状态绕过、终态复活和证据门伪造，否则任务可以在未批准或未真实执行时被置为 `done`。

七条里最要命的三条：

1. **`runner` 不检查任务状态就执行**——审批门形同虚设，副作用先于门发生
2. **`block` 能把 `done` 拉回 `blocked_on_human`，再 `approve` 复活**
3. **外层 `exit_code` 没进门条件**——agent 写完合法 manifest 再 `exit(1)` 仍判成功

第 3 条尤其典型：我写了一大堆 manifest 校验，却忘了看进程有没有正常退出。**五行代码的洞，盖住整个门。**

---

## 最终的门（7 条）

1. `artifacts` 非空，路径在自己 `work/` 内，是普通文件，`sha256` 必填且一致
2. 每个产物有 `produced_by`，指向生成它的命令
3. `commands` 是对象数组，`cmd` 非空
4. 每条命令有 `stdout_path`（真文件）和 `stdout_sha256`（重算一致）
5. 至少一条命令 `exit_code == 0`
6. `verdict` 非空
7. **外层进程 `exit_code != 0` 直接失败，不进入 manifest 校验**

---

## 四条教训

### 1. 门的强度 = 最弱那一环

我有 sha256、有 produced_by、有路径穿越检查，但只要外层退出码不看，前面全白做。

### 2. 让"没有工具的 reviewer"审文本，让"有工具的 verifier"做实测

两段分开。一个没有工具的模型永远无法实测，你逼它实测，它只会判 FAIL 或者编。

### 3. 模型会幻觉自己有工具

有一次它输出了 `<tool_calls>` XML，想调 shell。现在 prompt 里写死"你没有任何工具"，并把这类输出判废。

### 4. 断言写松了，测试会替你撒谎

有一条测试断言 `"must be running" in stderr`。函数名写错抛 `NameError`，traceback 里恰好包含这行源码——测试 PASS，功能没生效。

修法：断言同时要求正向特征和排除异常特征。

```python
# 松
"must be running" in stderr

# 紧
"ERROR runner refuses: task state" in stderr and "Traceback" not in stderr
```

---

## 一句话

**证据门不是"写一个检查"，是"逼自己接受最坏情况"的过程。**

每加一条，都会暴露上一条的假。四轮模型复核 + 一轮外部审查，才把它从一个摆设变成一道门。
