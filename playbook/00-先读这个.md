# 先读这个

给刚接触多智能体、并且手上只有轻量模型的人。

这个包不解释"什么是 agent"，只回答三个问题：

1. 多智能体为什么会翻车（21 条真实事故）
2. 用弱模型怎么才不翻车（12 条结构约束）
3. 最小可用的东西长什么样（能跑，30 项测试全过）

---

## 15 分钟跑通

```bash
cd starter
python bus.py init
python selftest.py      # 应输出 30/30 PASS
```

然后手工走一遍完整链路：

```bash
# 1. 派一张卡
python bus.py submit --agent researcher --title "读 RULES.md" \
    --payload '{"target":"RULES.md","ask":"统计规则条数"}' --nonce demo-001

# 2. 认领 + 开始（返回的 id 填进去）
python bus.py claim --agent researcher
python bus.py start --id <id>

# 3. 执行（runner 会建隔离目录、跑 agent、校验产物）
python runner.py --id <id> --cmd 'python "{ROOT}/demo/agent_research.py"'

# 4. 看结果
python bus.py status --id <id>
```

跑通之后你会看到 `runs/<id>/work/report.md`，里面有一节 `## 复现`，列着它跑过的每条命令和命令输出。

**这就是全部核心。** 剩下的都是在这上面加约束。

## 为什么是这三层

多智能体产品（Grok Bot、Cursor、任何"数字同事"）都是四层，但新手只需要理解三层：

```
控制面   谁该做、什么时候、能不能信   ← 状态机 + 证据门 + 审批
执行面   一个任务一个隔离目录 + 一个进程
上下文   只给它需要的，不给全部历史
```

**99% 的翻车出在控制面**，不是模型不行。证据门松了、状态机能复活、审批能绕过——再强的模型也会被坑。

所以这个包的顺序是：先把控制面做硬，再谈多 agent 协作。反过来做，你会得到一堆能演示、不能交付的东西。

---

## 三条最该先记住的

### 1. 没有验收标准的任务，强模型也会糊弄

`agent-bus` 里每个任务必须带 `accept`：产物文件、必须有的章节、要跑的命令。
没有判据的任务，模型会交一份"看着像样"的东西——你只能靠人肉判断，那就不叫自动化。

### 2. 让模型做"受约束的执行"，别让它做"开放式规划"

弱模型在开放式规划上会给你一个看似合理、实际跑不通的 DAG。
但在"读这个文件、按这个模板、输出这三个章节"上，它和强模型差距很小。

`docs/轻量模型守则.md` 整篇都在讲怎么把任务挪到后一种。

### 3. 状态放磁盘，上下文只是缓存

不要指望 agent 记住昨天的决定。把决定写进数据库、文件、任务卡。
每次给它一张卡 + 上游的五列结论，够了。

这条做对了，你的 agent 可以随时重启、随时换模型。

## 不建议做的事

- **不要一上来做群聊。** 协调收益在 2–3 个角色最高，超过 5 个互相污染上下文。流水线 + 独立核验比开会强。
- **不要用 CrewAI / MetaGPT 当骨架。** 它们解决"谁先说话"，不解决幂等、审批、证据、沙箱生命周期。你可以用它们做 demo，别用在要交付的东西上。
- **不要相信"agent 自己会判断"。** 判断要写成命令，写在门里。
- **不要在没有验收标准的情况下加 agent。** 加人只会让你多一份要人肉判断的输出。

---

## 一句话

**把不确定性压进结构里，而不是指望模型自己稳。**

这句话做到位了，轻量模型也能交付；做不到，最强的模型也只是让你更快地产生不可信的东西。
