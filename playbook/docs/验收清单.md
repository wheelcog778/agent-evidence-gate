# 验收清单

交付前照着打勾。打不上的就是还没做完，不要改判据。

## A. 每个任务（必查）

- [ ] 有唯一 `nonce`，重复提交不会产生第二条
- [ ] 有明确的 `agent`，不是"随便谁"
- [ ] 有 `deadline`（哪怕是 30 分钟）
- [ ] 有 `accept` 判据：产物文件名 + 必须含的章节 + 要跑的命令
- [ ] 产物路径在 agent 自己的 `work/` 里，不是任意绝对路径
- [ ] 失败时写清了原因，不是空返回

## B. 证据（必查）

- [ ] `manifest.commands` 是对象数组，不是字符串
- [ ] 每条命令有 `exit_code`
- [ ] 每条命令有 `stdout_path`，且该文件真实存在
- [ ] 每个 stdout 有 `stdout_sha256`，重算一致
- [ ] 每个产物有 `produced_by`，指向生成它的命令下标
- [ ] 产物 `sha256` 必填，重算一致
- [ ] 外层进程退出码为 0（不为 0 不许判成功）

## C. 核验（必查）

- [ ] 有一个**有工具**的 agent 做过实测（重算 hash、重跑命令）
- [ ] 有一个**无工具**的 agent 做过文本一致性审查
- [ ] 两份结论分开写：`实测：PASS` / `文本一致性：PASS`
- [ ] 没有任何一处只写"PASS"而不说是哪种 PASS

## D. 审批（涉及外部副作用时必查）

- [ ] 外发（消息/发布）、花钱、删除覆盖、改权限，四类都拦
- [ ] 未批准的任务不能被认领，也不能被 `--retry` 放回队列
- [ ] 审批超时按拒绝处理，不是一直等

## E. 状态（必查）

- [ ] 终态（done/failed/dead/cancelled）不能被改回其他状态
- [ ] 执行器启动前校验：状态= running、租约未过期、审批已过、未超期
- [ ] 崩溃的任务能被回收，attempts 有上限
- [ ] 同一任务不会被两个 worker 同时执行

## F. 上下文（交付前抽查一次）

- [ ] 下游没有吃到上游的全文，只吃结论与路径
- [ ] 四槽预算有硬上限，超了整槽丢弃并记录
- [ ] `used_bytes` 明显小于 `full_history_bytes`（否则说明没省）

## G. 交付物本身

- [ ] 解压到干净目录能跑
- [ ] 包内无密钥（`grep -rniE "sk-[a-z0-9]{16,}"` 为空）
- [ ] 包内有 SHA256SUMS，且逐个校验通过
- [ ] 已知缺口写在 README 里，没有藏
- [ ] 外部审查意见原文保留，逐条能对照到修法

---

## 最容易漏的三条

1. **B 的最后一条**：外层退出码。五行代码，堵住最大的洞。
2. **C 的第三条**：两种 PASS 不能合并。合并了就等于没做两段核验。
3. **E 的第一条**：终态可复活。测试里一定要有一条"先 done 再 block"的用例。

---

## 一条判断标准

如果你无法用一条命令证明某个结论，那这个结论就是"声称"，不是"验证"。

交付的时候，把"声称"和"验证"分开写。没人会因为你诚实而看不起你，但会因为你说"没问题"结果出问题而不再用你做的东西。
