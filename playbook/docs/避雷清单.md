# 避雷清单：21 条真的会出事的地方

每一条都来自真实事故，不是"最佳实践"摘抄。格式：**现象 → 后果 → 正确做法 → 出处**。

---

## 一、证据与验收

### 1. 只验"文件存在"，等于没验

**现象**：agent 写了个 `report.md`，你说"有产物，通过"。
**后果**：文件里可以是空的、可以是它抄的、可以是上一轮的。文件存在和交付成立是两件事。
**做法**：证据门至少四层——文件存在 → sha256 与声明一致 → 有对应的执行命令 → 命令的 stdout 也是真文件且 hash 对。
**出处**：`agent-bus` 的证据门从 v1 到 v4 改了四轮，第一轮只有"存在性"，被模型复核直接判 FAIL。

### 2. 命令是字符串，就等于"我跑过"

**现象**：`manifest.commands: ["python run.py", "sha256sum x"]`
**后果**：读者无法复算，也无法证明它跑过。这是自述，不是证据。
**做法**：每条命令是对象：`{cmd, exit_code, stdout_path, stdout_sha256}`。stdout 必须是真文件。
**出处**：同上，v2 改造。

### 3. 命令输出里带时间戳，hash 永远对不上

**现象**：日志第一行是 `started=2026-11-08T18:39:03`。
**后果**：重跑结果必然不同，`stdout_sha256` 不可复算，"可复现"是假的。
**做法**：复现清单里的命令必须是纯函数式的。时间戳写进另一个文件，不要进被 hash 的 stdout。
**出处**：模型复核第 3 轮指出，我改掉后第 4 轮才全 PASS。

### 4. 外层进程退出码不做门，写份清单再 `exit(1)` 也能过

**现象**：agent 写完合法的 manifest，然后崩溃退出。
**后果**：任务被标记成功，产物可能是半成品。
**做法**：`exit_code != 0` 时直接判失败，不进入 manifest 校验。这是最便宜也最容易被忘的一道门。
**出处**：Codex 审查 P0-6。

### 5. 断言写松了，测试会替你撒谎

**现象**：测试断言 `"must be running" in stderr`。函数名写错抛 `NameError`，traceback 里恰好包含这行源码。
**后果**：测试 PASS，功能根本没生效。
**做法**：断言同时要求正向特征和排除异常特征——`"ERROR runner refuses: task state" in stderr and "Traceback" not in stderr`。
**出处**：`agent-bus` 第 17 条断言假通过，实测出来的。

### 6. 畸形输入把校验器打崩

**现象**：manifest 里 `stdout_path` 指向目录，`sha256()` 抛 `IsADirectoryError`。
**后果**：校验器崩溃，任务状态不明。
**做法**：校验前先做类型检查；外层 `try/except` 兜住，崩了也要把任务判失败并写清原因。
**出处**：Codex 审查 P1。

## 二、状态与并发

### 7. 终态能被复活

**现象**：`block` 不检查当前状态，`done` 也能被改成 `blocked_on_human`，再 `approve` 放回队列。
**后果**：已完成的东西重新跑，可能覆盖产物。
**做法**：集中定义状态转移表；所有写状态的命令先查 `state in TERMINAL` 就拒。
**出处**：Codex 审查 P0-2。

### 8. 执行前不检查状态，门都白设

**现象**：`runner` 直接跑 `--cmd`，不管任务是 `queued` 还是 `blocked`。
**后果**：审批门形同虚设——副作用已经发生，后面的 `done` 门拦不住。
**做法**：执行器启动前校验：状态必须是 `running`、租约未过期、审批已批、未超期。四条任一不过就拒绝启动。
**出处**：Codex 审查 P0-1。

### 9. `--retry` 是绕过审批的后门

**现象**：未批准的任务 `fail --retry` 直接回队列。
**后果**：审批流被跳过。
**做法**：审批未过禁止 retry；attempts 用尽后无条件 `dead`，`--retry` 不能覆盖。
**出处**：Codex 审查 P0-3。

### 10. 两个进程同时发同一条外部消息

**现象**：`push --exec` 先查待发、再发、最后记账。
**后果**：同一条 PR 评论发两次、同一封邮件发两封。
**做法**：发之前先"抢占"——事务内 `INSERT ... WHERE NOT EXISTS`，抢不到就跳过；成功才落 `pushed`，失败删记录允许重试。
**出处**：`agent-bus` v0.2。

### 11. DB 写了、文件没写（或反过来）

**现象**：先 `COMMIT` 再写 inbox 文件，中间崩溃。
**后果**：数据库说交接了，文件里没有。
**做法**：文件写在事务内 + `os.replace` 原子替换；或者用 outbox 表记录待写、可重放。
**出处**：`agent-bus` v0.2。

### 12. 多条 SELECT 拼成一个"观测结果"

**现象**：`status` 先查 task 再查 events，中间有别的进程提交。
**后果**：输出里状态是旧的、事件是新的，人和 agent 都被误导。
**做法**：包一个读事务（`BEGIN` / `COMMIT`）取同一快照。
**出处**：Codex 审查 P1。

## 三、上下文与成本

### 13. 把上游长文整份喂给下游

**现象**：A 写了 10KB 报告，B 的 prompt 里全文贴进去。
**后果**：B 的上下文被吃掉一半，判断质量下降，成本翻倍。
**做法**：上游只交五列结论（时间/要什么/做了什么/产物路径/下一步），正文留在文件里，要细节按小节读。
**出处**：AGENTS.md §5 的交接协议；`agent-bus` 的 packet upstream 槽 2048B。

### 14. 预算说"硬上限"但截断标记不算钱

**现象**：`_clip(text, 1024)` 返回 1024 字节正文 + 14 字节 `…[truncated]`。
**后果**：实际输出超过上限，所谓硬上限是假的。
**做法**：截断标记算在额度内；预算不足时允许返回空，不要强塞 256 字节。
**出处**：Codex 审查 P1。

### 15. 静默失败：报"没发现"和"没跑"长得一样

**现象**：定时任务输出"今日无新内容"。
**后果**：你分不清是真没有，还是根本没跑起来。
**做法**：例行任务必须报"扫了什么、扫了多少条"，不报"发现了什么"。
**出处**：Grok Bot 用户踩过的坑（官方文档里写着）。

### 16. 沙箱里的 cron 会在镜像升级时消失

**现象**：把定时任务写进容器/VM 的 crontab。
**后果**：镜像一升级，调度全丢，而且没人知道。
**做法**：调度放在控制面（宿主/计划任务/网关），到点再唤醒沙箱。
**出处**：Grok Bot 用户反馈 + 逆向分析。

## 四、多智能体结构

### 17. 群聊超过 5 个就开始互相污染

**现象**：8 个 agent 拉群，都想发言。
**后果**：上下文互相干扰，token 爆炸，结论互相矛盾。
**做法**：协调收益在 2–3 个角色最高。Grok Bot 官方上限也就 2–6 个。研究/回测/审计这类活，流水线 + 独立核验比开会强。
**出处**：Grok Bot 官方限制；实测。

### 18. 用 supervisor LLM 做编排

**现象**：让一个模型决定"下一步谁做"。
**后果**：不可预测、贵、容易刷屏。
**做法**：编排是确定性程序——谁拿任务、什么时候截止、递归多深，由代码定；模型只回答"做什么、说不说"。
**出处**：Grok Bot 的 Room 轮次是程序编排，模型返回 `SENT` / `PASS`。

### 19. 按"名字"路由，不按 ID

**现象**：按群名/频道名匹配目标。
**后果**：同名群误投——Grok Bot 有用户把私人财务 Bot 的余额发进了公司 Slack，就因为群名和频道名一样。
**做法**：渠道绑定只用不可变 ID；含敏感数据的外发要目标确认。
**出处**：Grok Bot 真实事故（逆向分析里有）。

### 20. 每个 agent 一个独立"群聊系统"

**现象**：agent 一套表，群聊另一套表。
**后果**：transcript、未读、通知、权限全部要写两遍，而且永远不同步。
**做法**：群聊和 agent 是同一张表的两行（`kind: agent | room`），只多一层轮次编排。
**出处**：Grok Bot `GrokBotAgentKind {AGENT, ROOM}`。

### 21. 拿 token 当防伪凭据

**现象**：每轮生成随机 token 写进环境变量，让 agent 回显。
**后果**：agent 能读环境变量，这只是防重放，防不了伪造。留着会让人以为更安全。
**做法**：承认边界——不可伪造的只有"执行器自己记录的日志"和"外层退出码"。要么上只读文件系统 + 进程签名，要么明说这层只能防重放。
**出处**：我自己踩的，Codex 审查 P0-5 指出来，我把它删了。

## 用这份清单的正确方式

不要一次全上。按出事概率排序，先做这四件：

1. **外层退出码做门**（第 4 条）—— 五行代码，堵住最大的洞
2. **命令带 stdout 与 hash**（第 2 条）—— 让"我跑过"变成可验证
3. **执行前查状态**（第 8 条）—— 审批才有意义
4. **上游只给结论**（第 13 条）—— 立刻省一半上下文
