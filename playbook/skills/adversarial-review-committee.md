# 多空审核委员会（advocate / attacker / auditor）

一个进程内的三角色评审：**多头（主张）→ 空头（攻击）→ 审核（否决/打回）**。
适用于「有硬约束、且叙事能轻易绕过硬约束」的决策：选股信号、法律文书红队、合同审查、方案评审。

核心不是让三个模型聊天，而是：**硬规则用代码判，模型只负责论证与质疑；审核拥有真正的否决权；可修复的缺陷退回重报，改不动的直接淘汰。**

## When to Use

- 用户要求「多/空/审核」「红队」「挑刺」「质疑打回」「三方评审」。
- 一个决策同时满足：有可编码的硬约束（风控、合规、预算、时限），且存在大量看似合理的叙事。
- 不适用：开放式创意讨论、没有判定标准的头脑风暴。

## 结构

```
证据包 evidence ──> 多头 opinion ──> 空头 attacks ──> 审核 verdict
                        ↑                                   │
                        └──── 打回重报（仅代码级可修复项） ←──┘
```

- **证据包**：只放决策需要的派生字段（价格、比率、门槛、数据质量、组合约束），不放原始数据表。字段名稳定，模型才能引用。
- **多头**：结论 + 信心 + 3 条带数字的理由 + 可执行计划（价格/仓位/目标）+ 前置条件。
- **空头**：按 high/medium/low 分级的攻击，每条必须引用证据包里的数字，另给「什么情况下我承认自己错了」。
- **审核**：先跑代码硬检查，再让 LLM 补软质疑。硬检查非空 → 必须 REJECT，模型无权推翻。

## 硬规则归代码

这些必须写成确定性函数，不能交给模型：

1. 资格/范围（板块、主体、时效）
2. 数据完整度（字段缺失、快照过期、样本不足）
3. 数值上限（风险预算、止损、仓位、金额）
4. 可执行性（买不足1手、预算不够、时间窗已过）
5. 组合/资源冲突（槽位占用、同赛道叠加、重复占用）
6. 结论门槛（评分、盈亏比、必备条件数）

模型只补：逻辑一致性、反例、隐含假设、最坏情形。**「模型可以被说服，规则不行」是整个结构成立的前提。**

## 打回循环

- 区分 **可修复** 与 **不可修复**：
  - 可修复 = 改价格、改仓位、改手数、改挂单方式（代码能重算）。
  - 不可修复 = 资格不符、门槛不够、数据缺失、时间窗已过 → 直接淘汰，不要浪费第二轮。
- 只有**代码产生的修正项**才触发重报；LLM 的「修正建议」降级为建议，写进条件清单，否则模型会无限挑剔。
- **标签与轮次必须一致。** LLM 的修正项降级后，报告里写成「建议：…」，不要仍标成「打回」；否则会出现「打回」但轮次=1 的自相矛盾，用户会以为循环没执行。只有真正触发重报的代码级修正才配「打回」二字。
- 最多 2 轮；每轮记录 `round / agent / verdict / points / source`，报告里显示「几轮」。
- 三种终态，映射到明确动作：`通过`（可执行）/ `条件通过`（先满足前置条件）/ `打回淘汰`（不做）。

## LLM 输出契约

每个角色单独 system prompt，要求只输出 JSON：

```json
{"verdict":"支持|有条件支持|放弃","conviction":1,"thesis":"...","points":["..."],"conditions":["..."],"position_pct":0}
{"verdict":"反对|质疑|认可","pressure_points":[{"point":"...","evidence":"...","severity":"high|medium|low"}],"worst_case":"...","falsifiers":["..."]}
{"result":"PASS|DOWNGRADE|REJECT","comment":"...","soft_fails":["..."],"fixes":["..."],"conditions":["..."]}
```

- 解析失败/超时/无 key → 回退到规则版同结构输出，主流程不中断；报告里标明 `source=rule|llm`。
- 记录调用次数与失败次数，别让「LLM 版」在静默中退化成规则版。
- **按角色给足 max_tokens。** 空头/审核的 JSON 比多头长得多（6 条带证据的质疑、最坏情形、证伪条件），统一给 900 会在第 5 条被截断 → 解析失败 → 静默退回规则版。起步：多头 900 / 空头 1500 / 审核 1100；回退次数必须显示在报告头部。
- 证据包里给**派生指标**（如 `atr_pct`、`stop_atr_multiple`），否则模型会拿百分比和绝对值比较，编出「止损小于1倍ATR」这种看似专业的错话。

## Pitfalls

- **让 LLM 当硬规则裁判。** 它会被多头的故事说服，把「止损超限」解释成「结构特殊」。硬规则必须返回布尔值和原因，模型只能在其之上加软意见。
- **把 LLM 的 fixes 当作打回条件。** 模型每轮都能挑出新毛病，循环永远不收敛；只让代码级修正触发重报，其余写进「前置条件」。
- **空头没有数字。** 不强制引用证据包，它会输出「可能有利空」「注意风险」这类废话。要求每条攻击绑定一个字段或数字，并在 prompt 里给出字段名。
- **审核只会说「通过」。** 如果审核从没打回过，检查硬规则是否真的在跑；用合成用例验证 REJECT 路径。
- **只测 happy path。** 至少四个用例：全过、硬伤淘汰、非执行时点降级、可修复→重报→通过（断言轮数=2）。
- **角色共用一个 prompt。** 三个角色必须各有 system prompt 和输出 schema，否则会互相附和。
- **把「条件通过」当「通过」用。** 条件通过必须列出可核验的前置条件；没有条件清单的降级等于放行。

- **把委员会当 alpha 来源。** 它提高的是纪律、可解释性和复盘质量，不是胜率；模型不知道公告、板块轮动、盘口。对外表述要把「审计工具」和「预测能力」分开，否则用户会拿它当荐股产品。

## Verification

- 四个合成用例全过，且断言了终态与轮数。
- 临时关掉一个 LLM key，确认规则版仍能产出同样的 JSON 结构。
- 报告必须显示：每角色的结论、硬伤/建议分栏、前置条件、LLM 调用与失败次数。

## 交付

- 每个候选一张卡：多头/空头/审核三栏 + 计划条（买/损/目标/手数/最大亏损）+ 前置条件 + 数据质量。
- 附全局：硬规则清单、参数表、终态统计、LLM 调用/失败次数。
- 中文、具体数字、不写「可能/或许」；结论必须能落到一个动作。
