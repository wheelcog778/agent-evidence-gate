# 审计另一个 agent 的产物

> 目标不是证明它错，是把「可复算 / 只核到自洽 / 无法核」分开。
> 它写的 hash、测试数、`PASS` 都是**自述**，不是证据；只有你亲手跑出来的输出能进结论。

## When to Use

用：
- 用户说「检查 / 复核 / 看一眼 X 这几天的产物、交接、改动」；
- 收口方要把 `交接\inbox\` 的声称并入索引之前；
- 你打算在自己的报告里引用另一个 agent 报的数字。

不用：自己刚写完的东西（写完读回即可）；只是读它的报告给意见（那是一次阅读，不是审计）。

## 证据分级（先定这条，后面全是执行）

| 级别 | 来源 | 能写进结论吗 |
|---|---|---|
| A 自述 | 交接行、报告正文里的「已通过 / 12/12 / hash 一致」 | 不能 |
| B 它自己的日志与清单 | `verification.json`、`*.log`、`manifest.json` | 只能写「它记录为…」，不能写「已核验」 |
| C 你亲手重跑 | 你在副本上跑出的 stdout / exit code / 重算值 | 能 |

拿不到 C 的项，就在报告里明写「只核到自洽」。这是允许的结论，不是失败。

## 1. 把声称抽成表（先做，别边读边核）

从 inbox / 交接行里抽**可断真假**的字段：路径、字节数、行数、SHA256 前 8 位、测试数、门禁计数、样本数。
摘要性形容词（「完整」「充分」「全过」）不进表，留到第 4 步读正文。

```bash
# 一条命令全比对，不要一条条 read
echo '[
  {"label":"修复报告","path":"C:/proj/docs/修复-2026-11-06.md","bytes":11204,"lines":101,"sha256_prefix":"DDCD7E4D"},
  {"label":"结果清单","path":"C:/proj/reports/x/manifest.json","sha256_prefix":"11E6C097"}
]' > claims.json
python scripts/verify_claims.py claims.json
```

判定：`OK` = 字节/行数/hash 全对上；`FAIL` = 至少一项不符。
**FAIL 不等于造假**：会追加内容的文件（待批、任务板、日志）在交接之后又长了，hash 必然变。记成「失效，原因：后续追加」，不要写成「它报错了」。

## 2. 亲跑校验器 —— 一律在副本上

- `cp -r` 到 scratch 再跑。校验器常会重写 `verification.json`、新建 `results/dev-<时间>/`；在原目录跑等于篡改证据，下一轮审计就分不清是谁写的。
- **校验器依赖兄弟目录时，复制父目录，别只复制它自己。** 常见写法是 `ROOT.parent/'<另一个产物名>'/case/case.json`；单拷一个目录会直接 `FileNotFoundError`，看着像产物坏了。
- Python 校验器前面加 `PYTHONPATH=`：项目 `tools/` 里常有同名 `test_*.py`，否则 `unittest discover` 会报 `module incorrectly imported from …`——是模块名冲突，不是测试失败。
- 先跑「校验器」，再跑「测试套件」。校验器给的是数字表，测试给的是回归；两者不能互相代替。

## 3. 回读一手材料

抽 2–3 个关键数字或条文，回到原始件（PDF 抽出的 txt、保存的 HTML、`requests.jsonl`、DB）里 grep 一遍，和报告表格对齐。只核「报告 → 原始件」这一跳，不替它重做领域判断。

## 4. 读正文，找「声称与范围」的错位

这一类错位比编数字常见得多，只有读正文才看得出：

- **本轮没跑却说通过**：翻 `verification.json` 里有没有 `existing_regression_suites_rerun=false` 这类字段；「43 项全过」可能是上一轮的结果。
- **单 agent 自审说成复核**：`model_role_rerun=false` / `external_model_calls=0` 时，门禁计数是它一个人的再裁决，不是流水线输出。
- **副本级修复说成已修**：查 `deliverable` / gate 字段；改的是 `_runs/` 副本、产品没动的，记 `done(副本)`。
- **检查器 exit 1 只留在日志里**：`version_lint` / `doctrine_check` 的退出码若没写进结论段，就属于「已知问题未上报」。

## 4.5 停止条件类声称：核「真的没跑」和「跑不跑都一样」

被审方说「按预注册停止条件停数、未发布结论」时，两步都做，缺一不可：

1. **核它真停了**：读 `STOP.json` / guard 日志原文，并看输出目录里有没有 `summary`、逐日结果、汇率表——只有 manifest/artifacts 不等于发布了结果。两类证据对不上就是「声称停但留了结果」。
2. **核阻断条件是否触及任何分析行**：用目标列定「目标可用上界」（如 `select max(date) from panel where ex5 is not null`），与冻结上界比；再想一遍这些日期在管线里还要过哪些过滤与分档。

写结论时守四条措辞——这四条是最容易被同侪打回的：

- **「目标可用上界」不等于「有效末日」。** 目标非空只说明这一行进入候选；之后还有 `zt==0`、行业当日≥3 只、每档≥20 只等逐日过滤与分档，最终有效日数没跑就只能写「上界」。
- **不要给跨总体的比例。** `ex5` 有值日期数不能当用 `ex1` 的变体分母；「少 2 天 / 1,427（0.14%）」这种数没有分母基础，只能写「可能少 2 天的候选记录，实际影响未复算」。
- **「零影响」要限定到具体管线。** 限定「面板、目标值定义、逐日规则都不变」时，末尾无目标值的日期不新增目标观察；但诊断计数（行数、日期数、缺失数）会变，真实统计仍未执行。不能写「所有输出一致」。
- **行数与「ret 无空」不认证完整交易日。** 它只描述现有面板的记录情况，不能排除半日追加或行情缺口；单只缓存的末根 bar 也不代表全部股票缓存。

只给事实和等价做法，不替人定口径；若阻断确实改变样本，仍按二选一交人。

## 4.6 核对的是「评审意见」而不是产物时

用户转来别的 agent 的评审/审计意见时，要的不是照单全收，是判每条真假。先把每条意见改写成可证伪的命题，再按代价从低到高核：

1. **文件存在性**：说「X 不在包里」→ `ls` 目标目录并 `grep` 清单文件。同名变体（`census_<ts>.json` / `summary_<ts>.json`）经常两个都在，只是评审看的是更早那版包。
2. **依赖关系**：说「A 的数字依赖 B」→ 读 A 的生成脚本，看它 `read_text` 了谁。靠目录里文件并存推断依赖，经常是错的。
3. **数值一致性**：说「复核的不是最终 run」→ 把两个 `summary.json` 拍平，取字段交集，打印值不同的键 + 只在一侧存在的键。「62 个同名字段只有 `generated_at` 不同」是可引用的结论，「看着差不多」不是。
4. **统计量**：MDE、HAC、bootstrap 一律重算，并写明取了哪种方差（naive 与 HAC 取大）。对方方向对、量级可忽略时照写这一句，不要因为结论没变就跳过。
5. **查它没说的**：它读的那份文件里还有哪些字段/代码没看，结论依赖的最硬前提它有没有碰。评审的盲区通常不在算错，而在没读。

判级只有三种：真 / 部分真 / 不真。**文档不一致 ≠ 结论错误**：主数字逐位相同时，要修的是 run 链接与索引，不是重跑；反过来，数字对得上也不能替它补上没有的覆盖面。

## 4.7 收到一整个研究包：先验包，再验数，最后判它能否替代旧版

用户转来另一个 agent 的「完整包 / 475 文件已校验 / 12 项单测 / 请查收」时，四步，顺序不能反。

1. **验包（5 分钟）**：`zipfile.testzip()` 为 None、`sha256sum -c SHA256SUMS.txt` 全 OK、解压后文件数 = 清单行数 + 清单自己 + 未入清单的说明件。中文名 zip 在 git-bash 的 `unzip -l` 里是乱码（GBK 名没打 UTF-8 标志），用 Python 逐条 `info.filename.encode("cp437").decode("gbk")` 解出再落盘，不要据乱码判断文件缺失。
2. **验冻结顺序（2 分钟，最容易被跳过）**：读 run 的 `summary.json` 里 `gate.prereg_sha256`，与预注册文件 `sha256sum` 对；再看冻结前最后一次 run 的 `args.coverage_only` 是否为 true。解压会重置 mtime，文件时间不能当证据；`coverage_only=true` 且主实验在其后，才算干净。冻结前那次若已带主终点数字，就是「看完再冻结」，按不可引用处理。
3. **独立复算 2–3 个头条数字（30–60 分钟）**：用**自己的代码**从原始缓存重建，不 import 它的脚本。选三类：一个组合/收益数字（等权均值差最敏感）、一个样本计数（普查通过数）、一个单截面统计量（IC 或分档）。命中标准是小数点后 3–4 位一致；自有实现与它在 0.1% 内即可，超出就追到代码差异。**「0 mismatch」的自复现不算独立复现**——它用同一套 stats 重算自己的旧产物，只证明口径没漂。
4. **判它能否替代旧版**：能替代就写「可作为新基线」，并列出下一版要改的文档口径；不能就写清哪条数字没复算出来。**哈希过的包不现场改**，勘误写进下一版或包外文件。

**平行字段要并排打印。** 一个 summary 同时有 20 日与 60 日块时，把两块同名指标拉出来对比：出现过 60 日块里写着 20 日的值（`mean_port_diff20` 两处完全相同），普通自洽检查抓不到，但把「60 日差 −1.72pp」改写成等权口径的 −2.77pp 后，结论强度完全不同。同名字段不等于同口径。

### 4.8 自己出的包，交付前用同一套先审一遍

出包和验包是同一个动作，只差在谁是作者。源目录跑通不算数——源目录有运行期 `db`、`runs/`、缓存，包里的副本可能是另一回事：

1. 打包脚本自己先跑一遍测试，不过就拒绝打包；
2. **解压到临时目录，在解压后的副本里再跑一次测试**，这是唯一能证明包自洽的动作；
3. 全量校验包内 `SHA256SUMS.txt`（不是抽查前几条）；
4. 泄漏扫描 `sk-…` / `api_key=` / 真实 key 字样，命中就重打；
5. 报尺寸与包本身 sha256，并在交付说明里写清不包含什么（`db`、`runs`、密钥）。

包内文件清单要与磁盘对得上：`INCLUDE` 列表里有的才算，缺的显式打出来，不要静默跳过——跳过的那一条就是下一次「怎么少了个文件」。

## 5. 边界核查（五件套，各一条命令）

```bash
git status --porcelain | grep -v '^??'      # 已跟踪文件有没有被改
find src dist -type f -newermt "<起始日>"   # 本体有没有新文件
ls -la --time-style=+%m-%d_%H:%M <交付目录>  # 交付包 mtime 有没有动
grep -rIlE "sk-[A-Za-z0-9]{20,}|api[_-]?key.{0,4}=.{0,4}['\"][A-Za-z0-9]{16,}" <产物目录>
ls -la <AGENTS.md> <RULES.md>; ls <locks 目录>  # 规则文件、存留锁
```

原件 hash 用产物自己的 `verification.json.source_files` 比对（它已登记预期值），比重新挑样本快。

## 6. 判级：证据层 / 治理层分开写

- **证据层**：数字能否复算、边界是否守住、结论是否偏保守。
- **治理层**：版本漂移、任务板 `done` 语义、索引是否落后、有无「当前口径指针」、未跟踪的工具目录。

一句话先给形状：**「证据层合格，治理层有洞」**，再展开。不要写「整体良好」——那等于什么都没说。

治理问题按能否立刻修分级：
1. 能当场修且低风险（索引补行、归档旧行、`_moves.json`）→ 当轮修，写进报告。
2. 需要人拍板（版本号怎么补、方向是否封存、是否放开本体）→ 列成 2–3 个二选一，别替用户决定。

拍板项一次问完，别拆成三封小问题；机械修复当轮做掉，不要塞进问题列表充数。

### 6.5 跨项目进度评估（「这几天进度怎么样」）

用户要的是判断，不是清单。三个数分开报，别合成一句「整体良好」：

- **工程线（能不能跑）**：任务注册与真实运行、测试数、产物可打开、哈希对得上。
- **研究线（关掉几个问题）**：数每天闭合的判断题（判死 / 判可行 / 判不可得），不数文档与字数。四天 98 份 md 只闭合 1 个问题，是研究停滞，不是高产。
- **待批队列**：未决项增长快于闭合速度，系统就在空转。能按默认值当场结掉的（调度参数、内部实现、是否改名）不要推给用户；只有花钱、改规则、动产品本体才上待批，并压成一行 yes/no。

**任务板空着而 agent 都在线 = 工作在自我发明**：新任务来自「能做什么」而不是「证据指向什么」。这条要直说，附 board 行数、inbox 主题、当日新增文件数作证据。结论先给形状（「工程快、研究停」），每条判断后面跟一个可核数；顺手发现的自伤（如「已注册」但笔记本上根本不会启动）当场修掉再报，不要只列为风险。

## 7. 落盘与汇报

**默认不落报告**：三句话——证据层结论、治理问题条数与最重一条、下一步。只有出现 P1、用户要求留痕、或要把问题清单交回被审方时，才写 `审计/<日期>-<对象>产物核查.md`，七段：范围与方法 / 逐项复核表（声称 vs 我做的验证 vs 结果）/ 边界表 / 问题按优先级 / 判级 / 重算命令 / 没覆盖什么。为一次性核查再造一套模板，本身就是复杂度。

用户点名要「任务进度报告单」（给人看的一页式）时不是审计报告：按 `workspace-curation` 技能的「进度报告单」参考文档出单页 HTML，本 skill 的「我复跑 / 它实跑 / 它记录」三级标注照旧生效；审计三句话留在回复正文，不要塞进页面。

写回按 `workspace-curation` §5：索引 §四 一行、inbox 一行、移出行进归档并记 `_moves.json`。报告里保留你亲跑的命令，不要用「已核验」四个字代替。

汇报只给三件：证据层结论一句、治理层问题条数 + 最重的一条、报告路径。不复述核查过程。

## Pitfalls

- **hash 写在会追加的文件上必然过期。** 待批 / 任务板 / 日志会被后续回执加长；交接里写死 hash，隔天就对不上。要写就写「截至时刻 + 行数」，或在核对时注明「该 hash 对应 33 行版本」。
- **`done` 不等于产品修好。** 先看 `deliverable` 与 gate；副本级修复、`deliverable=false` 的任务板行要在审计报告里点名。
- **校验器自己也会说谎。** `verify_*` 常只验「daily.csv 与 summary 自洽」；看它 checks 列表里有没有「从原始数据重建」这一项，没有就写「只核到自洽」。
- **门禁计数变化先问方向。** pass 19→16、blocked 5→8 可能是撤回了过度确定的判定，不是回归失败；读理由段再判。
- **它记录的 exit code 可能是包装层归一的 1。** 执行器常把所有非零返回压成 1；拿同一条命令用 bash 直调、PowerShell `$LASTEXITCODE`、Python `subprocess.run().returncode` 各跑一次，三个值不一致就说明它记录的不是进程返回码，据此写下的「与文档不符」结论要撤回。
- **你读到的状态可能已经过期。** 审计期间被审方常还在跑：落笔前重读目标文件与 mtime；已被它自己改过的项要改成「已于 HH:MM 修好，我核对了 diff」，别把旧快照当现状报。查不到是谁改的：`stat` 拿 mtime，再在 `AppData\Local\hermes\logs\agent.log` 里按分钟窗 grep `tool patch completed`（每行带会话 id）；同一 profile 可并行多个会话，别默认记在被审方头上。
- **目录件数不能从被截断的 `ls` 里数。** `ls 目录A 目录B | head -30` 会吃掉第二个目录或长目录的后半截，据此写下的「只有 N 个文件」必错。断言件数前用 `ls -1 <目录> | wc -l` 或 Python `glob` 数一遍；已经写错的必须在下一份报告里显式更正，别静默改。
- **报告里的时间从 `date` 取，不要估。** 写「13:45」而实际 13:38，会让心跳、时效判断和事后归属全错；心跳/时间列一律复制 `date '+%m-%d %H:%M'` 的输出。
- **别把它报的 hash 抄进你的报告当证据。** 你没算过的 hash 不是你的证据；要么自己算，要么写「它记录为」。
- **只有 hash 值、没有产生它的命令，仍然只是自述。** 报告里写 `sha256 = …` 却不给命令行与终端回显时，读者无法复现这个指纹，也无法确认有进程真的跑过——判 B 级，并在结论里明说「指纹本身不证明执行」。反过来，你自己写报告时，每个 hash 后面必须跟一条命令；否则下一个审计者对你做的事，就是你刚对它做的事。
- **全 home 的 `find -newermt` 会超时**（180s 不够）。按项目分次跑，带 `-maxdepth` 与 `-not -path` 排除 `AppData`、`node_modules`、`__pycache__`。
- **样例不足时不评价命中率。** 只有 1–3 条记录时，报告只能写「样本不足」，不能给比率。
- **改测试期望值 = 改产品语义，不是补测试。** 审计代码修复先 `git diff -- tests/`；旧断言变化按上游硬闸门处理（见 `design-doctrine` 同名条）：停、给选项、等人拍板，不要用「本轮授权」或「测试同步」吸收。
- **「文件已校验」通常是清单自校验。** 475 件里 473 条哈希全过，只证明包没坏、没被改动；它不证明任何一个结论数字算对了。包级哈希与数字复算是两件事，验收报告里分行写。
- **带 `SHA256SUMS.txt` 的交付包是只读的。** 补一句脚注、改一个错别字，都会让清单里几十条哈希同时失效，而包可能已经外发。这类修正写进下一版包的变更记录，或另发一份包外勘误；只有确认包未外发时才允许当场改包并重签清单，且重签后要重新解压复验，不能只改清单文件。

## 8. 把问题写回给被审 agent

用户常把审计结果交回给对方自检。这时报告要换成「问题清单」格式，每条固定七项：id / 级别 / 一句话 / 证据(C 级，带文件行号或字段) / 复现命令 / 影响 / 关闭判据。另加三节：

- **不是问题，别改**：方向正确但容易被误认为缺陷的（如 gate pass 19→16 是撤回过度确定、负结果不是失败），写明不要为了数字好看改回去。
- **只到 B 级的疑点**：单独列，声明不作指控，避免对方把「未核」当「你有问题」。
- **关闭标准**：禁止用「已复盘、已注意」关闭；每条必须给命令+原始输出或文件+行号。

问题清单本身不放宽判据、不替人类决定，需要拍板的列成二选一。

**争议与分工走共享讨论文件，不互相写 inbox。** 同机多 agent 时可建 `交接\讨论\<日期>-<主题>.md`（只追加）：一条三行——问什么 / 依据（文件:行或命令输出）/ 需要对方回什么；开头写明「这不是人类审批」。边界：讨论只解决做法与证据，不决口径、不替代 `locks\` 认领、结论不自动改任务状态。**两票不同时不要投票取中。** 把分歧改写成一天内能答的数据闸：先定判据数字（如「去重后事件 ≥300 走 A，<100 回退 B」）、再跑只读可行性检查、按结果分派；两人各自保留结论与理由写进裁决文件，不要合成一个双方都不认的折中。对方回帖指出你的表述过宽时，先按证据判对错：成立就改自己的文件并升版本号（保留 v1→v2 改动记录），不成立就写成「仅到 B 级」交人——别用讨论记录替代验证，也别沉默改掉。
